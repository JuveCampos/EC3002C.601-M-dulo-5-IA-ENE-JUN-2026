GET vs POST

GET

"Dame algo"

Los parámetros van en la URL.

Sirve para consultar datos que ya existen.

Ejemplo: PokéAPI, INEGI, clima.

POST

"Aquí te mando algo"

Los datos van en el body (JSON).

Sirve para enviar información al servidor.

Ejemplo: llamar a un LLM con tu prompt.

Las APIs de LLMs son siempre POST: les mandamos el prompt en el body.

Códigos de estado HTTP

Toda respuesta de API trae un status code. No solo 200.

200OK — todo bien.
401Unauthorized — falta el token o está mal.
403Forbidden — tu token no tiene permisos para eso.
404Not Found — el recurso no existe.
429Too Many Requests — te excediste el rate limit.
500Server Error — falló el servidor, reintenta después.

Siempre verifica con httr::status_code(respuesta) antes de procesar.

Headers y autenticación

Los headers son metadatos que acompañan la petición.

Dos headers clave para APIs modernas:

  • Authorization: Bearer <TU_TOKEN> — quién eres.
  • Content-Type: application/json — qué formato envías.
# Cargar el token guardado en .Renviron
api_key <- Sys.getenv("GEMINI_API_KEY")

# Construir los headers
mis_headers <- httr::add_headers(
  `Authorization` = paste("Bearer", api_key),
  `Content-Type`  = "application/json"
)
POST directo con httr

Si quisiéramos llamar a Gemini sin cliente, se vería así:

library(httr)
library(jsonlite)

url <- "https://generativelanguage.googleapis.com/v1beta/models/gemini-2.0-flash:generateContent"

# Cuerpo de la petición (se convierte a JSON)
cuerpo <- list(
  contents = list(
    list(parts = list(list(text = "Hola, ¿qué es una API?")))
  )
)

respuesta <- POST(
  url   = paste0(url, "?key=", Sys.getenv("GEMINI_API_KEY")),
  body  = toJSON(cuerpo, auto_unbox = TRUE),
  content_type_json()
)

fromJSON(content(respuesta, "text"), flatten = TRUE)

Funciona, pero es frágil. Preferimos un cliente.

APIs de LLMs

Las APIs de LLMs tienen particularidades:

  • Son POST con un body estructurado (mensajes con roles).
  • Aceptan un system prompt para darle personalidad o instrucciones.
  • Devuelven texto generativo (no datos tabulares).
  • Cuestan dinero por tokens de entrada y salida.
  • Tienen rate limits estrictos (OpenAI: RPM, TPM).

Por eso existe {ellmer}: para no reescribir todo esto a mano.

ellmer: cliente unificado
La forma fácil

{ellmer} es un cliente unificado para LLMs hecho por Posit.

  • Mismo código para Claude, OpenAI, Gemini, Ollama.
  • Maneja autenticación, retry, streaming, tool use.
  • Lee las llaves de .Renviron automáticamente.
  • Soporta salidas estructuradas (JSON validado).
install.packages("ellmer")
library(ellmer)
chat_google_gemini()

Crear un chat con Gemini es una sola llamada:

library(ellmer)

# Asume GOOGLE_API_KEY en .Renviron
chat <- chat_google_gemini(
  model = "gemini-2.0-flash"
)

# Mandar un mensaje y obtener la respuesta
respuesta <- chat$chat("Explícame qué es una API en una oración.")

respuesta

El objeto chat recuerda el historial por defecto.

Verifica el nombre exacto de la función en ?ellmer — la API del paquete evoluciona rápido.

System prompts

Un system prompt define el rol y las reglas del modelo antes de empezar.

chat <- chat_google_gemini(
  system_prompt = "
    Eres un moderador experto en redes sociales.
    Clasificas mensajes en español como discurso de odio o no.
    Responde siempre en formato JSON con los campos:
      - es_discurso_odio (TRUE/FALSE)
      - razon (string corto)
  ",
  model = "gemini-2.0-flash"
)

chat$chat("Todos los aficionados del otro equipo son unos idiotas.")

Buen system prompt = respuestas consistentes y útiles.

Salidas estructuradas

En vez de pedir JSON en el prompt, podemos garantizarlo con tipos:

library(ellmer)

# Definir el esquema de salida
tipo_odio <- type_object(
  es_discurso_odio = type_boolean(
    "TRUE si el mensaje contiene discurso de odio."
  ),
  razon = type_string(
    "Explicación breve en español."
  ),
  confianza = type_number(
    "Confianza del 0 al 1."
  )
)

# Extraer datos estructurados
resultado <- chat$chat_structured(
  "Todos los del otro equipo son unos idiotas.",
  type = tipo_odio
)

resultado$es_discurso_odio  # TRUE / FALSE
resultado$razon
Ollama: LLMs locales

Ollama es un servidor que corre LLMs en tu propia máquina.

Ventajas

  • Gratis (no hay costo por token)
  • Privado (los datos no salen)
  • Sin rate limits
  • Funciona sin internet

Desventajas

  • Modelos más pequeños
  • Usa RAM y GPU
  • Más lento que las APIs de nube
  • Calidad menor que GPT-4 o Claude
# En terminal, antes de usar desde R:
ollama pull qwen2.5:7b
ollama pull llama3.2
chat_ollama()

El patrón es idéntico al de Gemini. Solo cambia el constructor:

library(ellmer)

chat_local <- chat_ollama(
  system_prompt = "
    Eres un clasificador de discurso de odio.
    Respondes solo TRUE o FALSE.
  ",
  model = "qwen2.5:7b"
)

chat_local$chat("Me encantó el partido de ayer.")
# [1] "FALSE"

chat_local$chat("Ojalá se muera ese jugador.")
# [1] "TRUE"

Ollama debe estar corriendo (ollama serve o la app).

Otros clientes API para R

Para APIs no-LLM, usa el cliente dedicado cuando exista:

Iterando APIs de forma segura

Para los 151 pokémon, iteramos con lapply() y protegemos con tryCatch():

library(httr)
library(jsonlite)

# Función que consulta un pokémon y maneja errores
consulta_pokemon <- function(id) {
  url <- paste0("https://pokeapi.co/api/v2/pokemon/", id)

  tryCatch({
    r <- GET(url)
    stopifnot(status_code(r) == 200)
    datos <- fromJSON(content(r, "text"), flatten = TRUE)

    tibble(
      id     = datos$id,
      nombre = datos$name,
      peso   = datos$weight,
      altura = datos$height,
      sprite = datos$sprites.front_default
    )
  }, error = function(e) {
    message("Fallo en id ", id, ": ", e$message)
    NULL
  })
}

# Iterar sobre los 151 y apilar
pokedex <- lapply(1:151, consulta_pokemon) %>%
  do.call(rbind, .)
Buenas prácticas al iterar
  • Pausa entre llamadas: Sys.sleep(0.5) para respetar el servidor.
  • Cachea los resultados en disco (saveRDS()) para no repetir llamadas pagadas.
  • Retry con backoff en códigos 429 y 500.
  • Guarda los tokens fuera del código con usethis::edit_r_environ().
  • Revisa el status code antes de procesar la respuesta.
  • Lee la documentación de rate limits de cada API antes de iterar masivamente.
# Cachear resultados para no volver a pagar
if (file.exists("resultados.rds")) {
  resultados <- readRDS("resultados.rds")
} else {
  resultados <- lapply(ids, consulta_pokemon)
  saveRDS(resultados, "resultados.rds")
}
